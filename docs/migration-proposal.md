# JSON State Files Migration Proposal

## Executive Summary

This document identifies JSON files in the application that store **application state** (not generated build products) and proposes migrating them to database tables for consistency, reliability, and maintainability.

### Key Findings

- **Total JSON files analyzed**: 100+ files found
- **State-storing files (authored)**: ~6 files outside of `wt-*` worktrees
- **Generated build products**: ~90 files in `graph/manifests/`, `scripts/graph-relationships.baseline.json`, etc.
- **Historical archives**: 10+ files in `docs/archive/`

### Migration Priority Matrix

| Priority | Files | Action | Reason |
|----------|-------|--------|--------|
| 🔴 High | `scripts/lib/laneCases.json` | Migrate to plandb | Critical runtime configuration |
| 🟡 Medium | `graph/method-leaf-baseline.json` | Migrate to algorithms.db | Test coverage metadata |
| 🟢 Low | `docs/archive/*.json` | Keep as-is or archive table | Historical documentation |
| ⚪ None | `graph/manifests/*.json` | Do NOT migrate | Generated build products |

## Detailed Analysis

### 1. Critical Runtime Configuration (HIGH PRIORITY)

#### File: `scripts/lib/laneCases.json`

**Current Purpose:**
- Defines branch-to-lane mappings for the record lane system
- Contains chain definitions for lane resolution
- Stores environment variable rules for lane derivation

**State Stored:**
```json
{
  "branchToLane": [
    { "branch": null, "lane": "main" },
    { "branch": "develop", "lane": "main" },
    { "branch": "voice/lexicographer", "lane": "voice/lexicographer" }
  ],
  "chains": [...],
  "env": [...]
}
```

**Migration Target:**
- **Database**: `plandb`
- **Table**: `lane_configurations`
- **Schema**:
  ```sql
  CREATE TABLE lane_configurations (
    id TEXT PRIMARY KEY,
    branch TEXT NULL,
    lane TEXT NOT NULL,
    chain TEXT NULL,
    env JSON NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );
  ```

**Rationale:**
- This is **critical runtime configuration** that determines how records are isolated per session
- Currently stored as a static JSON file, but should be database-backed for:
  - Version control with the plan store
  - Audit trail of lane configuration changes
  - Consistency with other plan-related data in plandb

### 2. Test Coverage Metadata (MEDIUM PRIORITY)

#### File: `graph/method-leaf-baseline.json`

**Current Purpose:**
- Stores baseline coverage metrics for TypeScript method leaf functions
- Used to track test coverage baselines across the codebase

**State Stored:**
```json
{
  "agent-stall.ts": 5,
  "aider.ts": 2,
  "app--detached-window.ts": 2,
  ...
}
```

**Migration Target:**
- **Database**: `algorithms.db`
- **Table**: `method_leaf_baselines`
- **Schema**:
  ```sql
  CREATE TABLE method_leaf_baselines (
    file TEXT PRIMARY KEY,
    baseline_value INTEGER NOT NULL,
    last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  );
  ```

**Rationale:**
- Test coverage metadata should be backed by the algorithms database
- Provides historical tracking of coverage changes
- Enables querying coverage trends over time

---

### 3. Historical Documentation (LOW PRIORITY)

#### Files: `docs/archive/*.json`

**Current Purpose:**
- Archive documentation of removed features
- Contains issue numbers and descriptions of deprecated functionality

**Examples:**
- `4204-deletion-track.json` - Deletion tracking feature archive
- `4280-plan-github-sync.json` - GitHub sync feature archive
- `clusters.json` - Feature cluster documentation

**Migration Target:**
- **Option A**: Keep as-is (historical documentation)
- **Option B**: Migrate to `feature_archives` table in plandb

**Rationale:**
- These are historical records, not active state
- Can remain as documentation files or be migrated to an archive table
- Lower priority since they don't affect runtime behavior

---

### 4. Blueprint Manifests (MEDIUM PRIORITY)

#### File: `docs/blueprints/bsc-reskin/extension.json`

**Current Purpose:**
- Blueprint manifest with embedded prompts and stage definitions
- Defines the bsc-reskin blueprint structure

**Migration Target:**
- **Database**: `plandb`
- **Table**: `blueprints` (existing or new)
- **Schema**: See existing blueprint table schema

**Rationale:**
- Blueprints are already backed by the blueprint library
- The JSON file is a manifest that documents the blueprint structure
- Consider migrating to database for version control

---

### 5. Generated Build Products (DO NOT MIGRATE)

#### Files: `graph/manifests/*.json`, `scripts/graph-relationships.baseline.json`

**Current Purpose:**
- Generated by `graph-materialize` build process
- Contains crate definitions, dependencies, and manifest data

**Examples:**
- `bsc-runtime.json` - Runtime command manifest
- `bsc-blueprint.json` - Blueprint command manifest
- `plandb.json` - Plan database command manifest

**Rationale for NOT Migrating:**
- These are **generated build products**, not authored state
- They are regenerated by the build process (`npm run emit:manifests`)
- Migrating them would be redundant and could cause drift
- The record store (algorithms.db) already backs these records

## Migration Scripts

### Lane Configuration Migration

```bash
# Create migration script
cat > scripts/migrate-lane-config.sh << 'SCRIPT'
#!/bin/bash
# Migrate laneCases.json to plandb

JSON_FILE="scripts/lib/laneCases.json"
DB_PATH="$HOME/.base-studio-code/plans/plandb.db"

# Parse JSON and insert into database
sqlite3 "$DB_PATH" << SQL
CREATE TABLE IF NOT EXISTS lane_configurations (
  id TEXT PRIMARY KEY,
  branch TEXT NULL,
  lane TEXT NOT NULL,
  chain TEXT NULL,
  env JSON NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Insert from JSON file
$(cat "$JSON_FILE" | jq -r '.branchToLane[] | 
  "INSERT INTO lane_configurations (id, branch, lane, chain) VALUES (\(.branch), \(.lane), \(.chain);"')
SQL
SCRIPT

chmod +x scripts/migrate-lane-config.sh
```
