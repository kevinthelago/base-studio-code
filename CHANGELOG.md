## [Unreleased]

### Accessibility
- **Spoken fleet coordination — the app can now speak the coordination stream aloud so you can drive the fleet by ear (#3804, Tier 1 of epic #2725)** — the app's core surface is streaming PTY consoles, which screen readers handle terribly (flood or silence). But we control the *structured* coordination stream before it becomes terminal noise. With **Settings → Accessibility → Spoken coordination** enabled, new coordination events are spoken via the WebView's `speechSynthesis` — "api-stream is paused, waiting for you"; "ui landed a PR" — so a blind developer can steer the agents by ear. This is app-owned TTS, distinct from (and running alongside) #3770's ARIA live region, which the user's own screen reader speaks. A new `useCoordSpeaker` hook reuses the same seam as `useCoordAnnouncer` (`useCoordLog` → `coordAlerts`, whose text is already the human line), speaking only the structured events, never the raw terminal stream. **Opt-in and OFF by default**; rate, voice, and verbosity (`terse` = only what needs you; `verbose` = adds progress like landings and ready gates) persist across restart, with a "test voice" button. The mount backlog is seeded silently and every event is remembered whether spoken or not, so enabling mid-session never buries you in history. Fail-safe: no engine (or off) → no speech, no errors. Engine + verbosity policy + the speaker hook are unit-tested.
- **The jsx-a11y interactive-element backlog is cleared — the guardrail now enforces keyboard operability (#3775, Tier 0 of epic #2725)** — #3773 shipped the jsx-a11y guardrail with the three interactive-element rules downgraded to `warn` (a grandfathered backlog). Those are now back at `error`, so a clickable element that isn't keyboard-operable fails the gate. The 21 real sites were resolved two ways: genuine buttons (clickable cards/rows, the Titlebar window controls, the switch/checkbox controls, the team card) now carry `role` + `tabIndex` + Enter/Space activation via a new shared `clickable()` / `onEnterOrSpace` helper (`@/shared/ui/a11y`) that **bundles** keyboard operability with the click so it can never drift off; the genuine non-button surfaces (modal/drawer/dropdown backdrops dismissed by Escape, drag-reorder strips, pan/zoom canvases, pointer-capture graph nodes, propagation-guard menu wrappers) each carry a documented per-site disable. So a keyboard or screen-reader user can now operate the cards, toggles, and window controls the app is built from, and every future interactive `<div>` must come through the helper or a real Button primitive.

- **A component's file is generated, so the gate sends the edit to the record — `bsc ui backing` (#4193)** — the graph is the source of truth and a component's file is the emitted artifact, but nothing told a worker that: it found the file, edited it, opened a PR, and the record kept the old body while the app went on rendering the record. `bsc ui backing <path>` answers "does this file have a record?" from the store's own `src` provenance — so it covers EVERY component, not only the pages in the frontend shadow catalogue (which is DEV-only and Vite-glob bound, unreadable from a `bsc` session). `bsc ui backing gate <path>...` turns that into the landing check: run it over `git diff --name-only` before opening a PR and it **exits non-zero**, naming the file, its record, and the two commands that fix it (`bsc ui set` then `bsc ui emit component`). Rejecting rather than warning is deliberate — a warning at landing time becomes noise and the drift accumulates anyway. The match is a suffix at a path BOUNDARY, so an absolute or worktree-relative path resolves while a bare filename never does (one filename backs many trees, and a gate that fires on those is a gate people route around). Two records claiming one file are both reported rather than one silently winning. **Components only, deliberately.** #4192 gave algorithms a round-trip, but a path-based gate cannot be honest about them: an algorithm record is a function lifted OUT of a file and several share one `src` — `sorts.ts` backs four records and also holds imports, types and a registry no record covers, so the same gate would either miss the real case or fire on legitimate edits. The algorithm half follows once this one has proven itself. `worker-protocol.md` carries the rule with both verbs, so the refusal reads as a step the worker skipped rather than an arbitrary no at the end of its work.
- **`bsc graph emit` — the algorithms library can finally write back out, so a fix is made to the RECORD and the file follows (#4192)** — the graph is the source of truth and a file is the emitted artifact, but only the COMPONENT library could round-trip: `bsc ui` had `harvest` in and `emit` out, while `bsc graph` had `harvest` and nothing back. So for an algorithm, "edit the record then re-emit" stopped at the first half — an agent could fix `impl set --code` and the file it came from still held the old body, with no command that would reconcile them. `emit impl <id> <dir>` · `emit all <dir>` · `emit sync <dir>` close it, modelled on `bsc ui emit` deliberately so the two libraries behave the same rather than each inventing a round-trip — including the provenance stamp whose `sha256` covers the body, which is what lets `sync` re-emit a MANAGED file and **skip a hand-edited one rather than clobber it**. **One place it must NOT copy the component emitter, and it is a data-loss difference rather than a stylistic one**: a component owns its file, but an algorithm is a function LIFTED OUT of one — in this repo's own graph, of 63 algorithms carrying provenance, **34 share their `src` with another impl** (`sorts.ts` alone backs four, `crates/cve/src/install.rs` another four), and those files also hold imports, types and registries no harvest ever lifted. Writing a record's code to its `src` would delete all of it. Each record therefore emits to its OWN file under the folder its provenance names — one record, one file, nothing overwritten. Three classes are reported rather than emitted, each with its reason, because silence reads as "nothing to do": a **primitive** (DESCRIBED via `--ref`, never re-coded, #2972), a record with **no `src`/`folder`** (no tree position — the message names the `impl set --src` fix), and one with **no code**. Verified against the live library: 102 of 118 records emit, the 16 skips are 13 primitives + 3 provenance-less, a clean `sync` reports 102 up-to-date, and a hand-edited file comes back as `diverged` with the edit intact. The stamp/hash/verdict contract moved to `bsc-cli-util::vendored` — shared by both emitters, because two copies of a drift detector are free to drift apart (#4181 is that exact joke one layer up).

The fallback matters more here than anywhere else, because this page is mounted for the whole session rather than one rail destination away: a record that will not load would be a Console that is never there, so it degrades to a re-seed prompt and `reconcileSeed` restores a `role: "page"` record from the packaged seed on every boot. Console joins the shadow catalogue, which puts it under the parity guard and the whole-catalogue browser check automatically — **all 9 pages now compile in Chromium**.

- **Glance renders from the graph — the cockpit was never the poor fit it was assessed as (#4185, epic #3604)** — the migration recipe had Glance down as *"a bespoke 732-line orchestrator, POOR FIT, recommended NOT migrating"*. Read again with seven migrations of hindsight, that objection was **size, not shape**: Glance is a Workspace composed of components with its behaviour in hooks and `lib/`, which is exactly the shape of every page already moved. So it moved — the workspace and the 8 components it composes are now **9 graph records** (`glancepage` + canvas, inspector, node, the two morphs, plan screen, chat dock, session log), mounted through the runtime loader by a `GlanceGraphHost`, with a `glanceGraphPlatform` registering the ~19 hooks and pure derivations the cockpit is thin over plus the other features' surfaces it composes. That check earned its keep immediately: it found **four unregistered modules** (`GraphCanvas`, `TabBar`, `IconButton`, `previewReview`) that the static boundary guard had passed, because that guard counts a record's `src` path as a resolution route and the loader has no such rule. jsdom cannot run esbuild-wasm, so this class of gap had no test before.

- **A designed page can now contain its own failures — `PageBoundary` is a kit primitive (#4172)** — #4170 gave the app's `Screen` a page-scoped boundary, but that resilience was welded into one app shell. The designer composes **specs** — data trees whose `type` must be a registered `PrimitiveName` — so an unregistered component simply does not render, and `PageBoundary` existed in `react-ui.json` only as a closure dependency of `Screen`, invisible to `bsc ui list` / `bsc ui schema`. Every page the designer composed, and every page a generated app renders, therefore had no failure containment: one throwing child blanked whatever hosted it, navigation included. It is now a first-class primitive — a `PrimitiveName`, a manifest spec, and a `registry.tsx` row (the three the sync test pins together) — in the **feedback** group beside `Banner`/`InlineError`/`EmptyState`, since what it renders is an error state. **Generalized for reuse in the same pass**: the #4170 version hard-coded this app's own wording ("pick one from the tabs above, or press Ctrl+← / Ctrl+→"), which is meaningless in a generated app — the headline, recovery hint and retry label are now props with neutral defaults, and `Screen` passes this app's wording. A fallback that tells you to press keys the app does not have is worse than no hint. It composes from **data**: every prop is plain, and the retry is internal, because a spec tree cannot carry a function — so a page wraps its body (or a `Slot` the host fills) and gets containment with no host wiring. The designer's `claude.md` carries it as a Standard, with the boundary between it and the expected-state components (`EmptyState`/`InlineError`/`Banner`) stated: a boundary is for unexpected throws during RENDER, not for an error you can predict.
- **Shadow mode — every migrated page is now built from the graph alongside the app, so "is this page ready to render from the graph?" is a list instead of a judgement call (#4169, step 1 of the graph-renders-the-app reframe)** — epic #3604 has been moving the app's own UI into the components graph a page at a time, and the open question was never "graph or files": it is *what fraction of a page is expressible as data, and how complete is the registry for the rest*. A toggle over an incomplete registry does not give a migration, it gives a fast way to render a shell that does nothing — #3605's "built, not mounted" state, and the reason Settings was rolled back to its hand-coded pages (#3758). So the soft signal comes first. `window.__bscShadow.run()` builds each page from the graph — vendoring its siblings exactly as the loader would (`@/components/<id>` and `provides` overrides), walking every specifier the compiled page will `require()`, and compiling the source through the same esbuild step the mount path uses — and reports per page: **graph-identical / differs in N of M nodes / unbound behaviours**, each unbound one named with the symbols it was to supply and the module that asked for it. The structural half compares the ELEMENT TREE, not the text: a graph record is its file with a generated header, the CSS import stripped and sibling specifiers rewritten, so a byte diff is all noise, while a changed skeleton is exactly the drift that matters. It **renders nothing and changes nothing** — no component mounts, nothing is written to the store, and the sweep runs only when asked, because reading the registry honestly means loading each feature's platform surface (a first-visit's worth of work) and doing that unasked would muddy the boot-cost picture this project measures. DEV-only by construction: the file half of every diff is a Vite `?raw` glob, so a production build drops the branch and emits none of it (verified against `vite build` — no chunk, no strings). The first sweep: **all 8 pages fully bound**, 6 structurally identical, `skillspage` **differs in 24 of 271 nodes** (`SkillsDigest` has diverged — the graph copy carries a `SkillsDigestBar` the file never grew) and `securitypage` in 1 of 290, while `settingspage` is graph-identical AND fully bound yet still renders from files. The catalogue is pinned to reality by test — every page record must appear in it, every declared file must resolve, and `rendersFrom` is read back out of `lazyWorkspaces.tsx` — because a page missing from a coverage report reads exactly like a page with nothing to report.
- **The algorithms harvest produces a reviewable shortlist instead of the tree relabelled (#4091)** — the librarian could already `bsc graph harvest` this app's own source, but the output was unusable: **3257 candidates, 1908 of them "worthy"** (59%), with React components swept in as algorithms, no way to trace a record to its file, and nothing that would ever appear in the graph UI. Four defects, fixed together, taking it to **2224 candidates and 291 worthy (13%)** with **zero components leaking** and full recall on `shared/lib/algorithms/*` — the known-good set. **Components are the component graph's, not the library's:** a function that renders JSX is skipped outright, decided by the tree-sitter node kind rather than a `<` scan (which would mistake every TypeScript generic for markup). The two harvests now partition the tree instead of both claiming it — `bsc graph harvest src` was lifting `PathExposeBanner` and the whole banner set. **Nested closures are not candidates:** `step` inside `useDockEntrance`, `tick` inside `usePoll`, `onKey` inside `useModalDismiss` — nothing outside the parent can even name them, so no scoring weight could fix a candidate that should never have existed; this was the bulk of the noise. The rule is deliberately **nesting, not export-ness**: a private module-level helper (this crate's own fixture has `function merge<T>`) is a real building block, and an export-only rule would have dropped exactly the primitives the library wants. **Every candidate now carries `src` and `domain`:** provenance so a record can be traced, deduped against a re-harvest, and joined back — ids are bare function-name slugs that collide freely (`dismiss.ts`, `approve.ts`, `app.ts` all recur) — and a facet, because per #3607 an impl without a `domain` does not surface in the graph UI at all, so a clean `curate --apply` used to land work nobody could see. The facet drops structural containers, so `shared/lib/algorithms/orderByRank.ts` is the `algorithms` domain rather than the `lib` one. **And the worthiness bar became architecturally load-bearing**: it is now the line between the LIBRARY and the app's own host code, so it asks *"would a different project reach for this?"* rather than *"does this look algorithmic"* — a React hook, a function that reaches the host/browser/store, or one living in a feature slice is glue however clean it reads. Raising the *threshold* was tried and is wrong: the `generic` signal fires on only ~80 functions here, so a higher bar starves out `shared/lib/algorithms` itself; the negatives carry the discrimination instead. Honest about its limits — this is a triage heuristic feeding a curator, not an oracle, and cheap textual signals cannot see transitive coupling.
- **A worker's context now carries the reference code for its feature's required algorithms (#4082)** — #4080 gave a feature a `requires` list, but nothing read it: the intent was recorded and changed no behaviour, so a worker still re-coded what the library already held. This is the payoff half. At fleet launch, `write_worker_context` resolves the stream's feature (`stream` = the worktree branch = the feature slug), looks each required id up in the global algorithms graph, and inlines the **actual reference implementation** — name, tech, summary and code — into the worker's `CLAUDE.local.md`, with an explicit instruction to reuse rather than re-derive, and an escape hatch to say so when one genuinely does not fit (a forced fit is worse than an honest re-implementation). Inlining is what makes the reference reachable at all: a `worker`'s restricted surface has no `bsc graph`, the same reason skills are inlined rather than left as a "read skills.md" note (#636). Both stores are read **in-process** — `plandb` and `bsc-graph` are already linked deps (the latter since #4078, precisely so a reader need not spawn a subprocess). Three cases are handled distinctly rather than collapsed: an impl **with code** gets a fenced block in its own language; a **primitive** (described via `--ref`, never re-coded) is named and explained instead of rendering an empty fence; and a **dangling id** is reported by name with an instruction to flag it — #4080 deliberately does not validate ids at plan-write time, so this is the first place a typo becomes visible, and silently dropping it would leave the worker believing the plan named nothing. Idempotent (the context is rewritten every launch and must converge) and best-effort at every step: an unreachable plan.db, an unreadable graph, a stream with no matching feature, or a feature requiring nothing all add nothing and never abort a launch.
- **A type-only import no longer counts as a missing dependency — 45 more components become harvestable (#4076)** — `bsc ui harvest` closes each candidate into a compilable module and reports an honest `buildable`, and it was counting **every** internal import as a dependency the closure must carry, including ones the compiler erases. `import type { Plan } from "@/…"` — and the inline form `import { type A, type B } from "…"` — is removed by esbuild's tsx loader *before it resolves anything*, so the module it names need never be in the closure at all. Harvest was blocking on imports the bundler never asks for: of this repo's 701 blocking import-slots, **147 were erasable**, and dropping them takes the frontend from **217 to 262** buildable candidates (+45) with **zero** records losing buildability. Every one of the 45 was verified against the *actual* esbuild-wasm build the preview runs — each former blocker is gone from the emitted code — rather than inferred from the loader's documentation. **The rule is SYNTACTIC and must stay that way:** `import { Plan } from "…"` where `Plan` happens to be a type is NOT erasable (neither harvest nor esbuild has type information, so the import survives), a MIXED clause (`{ run, type Plan }`) keeps the whole statement, and a specifier imported both ways stays a real dependency — the value import outlives the type-only one. `import {}` is not an erasure either; it survives as a side-effect import. **`doctor` learned the same rule in the same change**, because it is the half that makes the verdict safe: `graph_health` flags any unresolved internal specifier, so shipping harvest alone would have certified 45 components that `doctor` then condemned as `unresolvable-import` — the exact false accusation #3486 was filed for, in a new costume. - **Discovery plans for the cloud going down — a new `outage_response` dimension (#3989)** — the Discovery stage covered goal/scope/stack/architecture and ~20 applicable dimensions, but nothing in it asked the question a hosted app is most exposed to and least in control of: **what happens when a cloud dependency you do not own goes dark?** `reliability` covered the code-level bars (timeouts, retries, circuit breakers, RPO/RTO) and incident response got a single line about error tracking and a runbook — neither produces a plan for a region/AZ, the managed database, object storage, the auth provider, DNS/CDN, the queue, the payment processor, the email/SMS gateway, or the LLM provider being down. Instead the planner requires it per project (`bsc plan discovery require outage_response`) when the project is cloud-hosted or leans on third-party cloud services — the same dynamic-required-set pattern as `schema` for a data platform and `api` for a realtime service — and records the skip in `discovery/_skipped.md` otherwise. - **A torn-off window carries its tab, and dragging it docks the page back — the browser model (#3919)** — tear-off was one-directional: a detached window rendered a bare titlebar over the page, with nothing to grab, and the only way home was CLOSING it, which reads as discarding the page rather than returning it (#3917). - **A supply-chain block now lights the project node amber (#4008)** — when the gate (#3799) blocks a command for adding a malicious or known-vulnerable package, its only trace was one row in `perm.log` that nothing reads unless you run `bsc logs perm`. ### Security
- **`bsc-supply` — the install-time gate that blocks adding a malicious or known-vulnerable dependency (#3799, supply-chain #2433)** — the enforcement layer over the #3797 CVE data, and the companion to #3795 (scripts-off default): a compromised agent's `npm add <malicious-pkg>` is stopped *before* it installs. A new `bsc hook bash-supply` PreToolUse hook (alongside the `bsc-deny` dangerous floor) reads the Bash command, and when it's a dependency **add** (`npm/yarn/pnpm/bun add`, `pip install <pkg>`, `cargo add`) vets each package against OSV via the `cve` engine (cache-first) and `exit 2`-blocks — which fires under **every** posture, even bypass. The policy is precise and low-false-positive: a **malicious package** (OSV `MAL-…` advisory — the Shai-Hulud case) is blocked at any version; a **version-pinned** add whose exact version carries a vulnerability at/above the threshold (`$BSC_SUPPLY_MIN`, default `high`, matching `bsc cve scan`) is blocked; a versionless non-malicious add is allowed (the resolved version is unknown pre-install — `bsc cve scan` covers it after). It is **fail-open** — a non-install command, an OSV outage, or any engine error allows the command (the scripts-off floor is the always-on protection) — and every block or fail-open is logged to the perm log. Registered on **gated (agent) panes** only (like `bsc-scope`/`bsc-audit`), not the maintainer's manual console. The install-command parser (`crates/cve/src/install.rs` — scoped names, exact-vs-range versions, chained commands, value-flags like `-r requirements.txt`), `Advisory::is_malicious()`, and the block decision are all unit-tested; the `bsc-env` rc stays valid bash. Also fixes a latent bug the newly-run subshell test surfaced in the #3795 `bsc-build-allowed` helper: it returned the last loop iteration's exit status (non-zero when the last allowlist entry wasn't installed), so a clean run looked like a failure — now it always exits 0.
- **Fleet installs run with lifecycle scripts OFF by default, plus a trusted native-build allowlist (#3795, epic #2433)** — package lifecycle scripts (`preinstall`/`install`/`postinstall`) are the execution vector for supply-chain worms (Shai-Hulud and its kind): a compromised dependency runs arbitrary code the instant it's installed, and the audit confirmed the app had **no `--ignore-scripts`, no lockfile verification, nothing** — fleet agents `npm install` over unmediated Bash. Every fleet-worktree session now carries `npm_config_ignore_scripts=true` (set beside the shared package caches in `platform::pkgcache`, appended after the dir-precreate loop since it's a policy value, not a path), which npm, pnpm, and yarn-classic all honor — so an agent's install lands the dependency tree without running a single lifecycle script. Because npm has no per-package script gate, legit native builds are restored explicitly: a `@data`-embedded **build allowlist** (`data/permissions/build-allowlist.json` — esbuild, better-sqlite3, `@swc/core`, sharp, node-pty, …) is baked into a new `bsc-build-allowed` shell helper that, after an install, runs `npm rebuild` for exactly the allowlisted packages **present** under `./node_modules`, re-enabling scripts for that one invocation only — nothing off the allowlist ever runs a script. A first-party `no-install-scripts` skill teaches the posture (install normally → `bsc-build-allowed` for trusted natives → never re-enable scripts for a whole install). Host-side, where installs happen; the WSL sandbox ships no Node/npm. Allowlist names are charset-filtered before rendering so a hostile seed can't inject shell metacharacters. The `bsc-env` rc stays valid bash (the `full_bsc_rc_is_syntactically_valid_bash` guard), and a subshell test proves the helper rebuilds only the present allowlisted package with scripts re-enabled. This is the standalone scripts-off default; the CVE store + `bsc-supply` install-time hook + version-cooldown remain separate #2433 slices.

- **`bsc cad` keeps sharp edges — dual contouring (#3388, kernel #2621)** — the polygonizer ROUNDED every sharp feature, because surface nets places a cell's vertex at the mean of its edge crossings and the mean of points scattered around a cube's corner sits strictly inside the cube. Both `mesh.rs` and the crate README already carried *aspirational* comments promising dual contouring with nothing behind them; the implementation now exists and those comments are true. Each surface-straddling cell keeps **hermite data** — every edge crossing plus the SDF gradient (surface normal) there — and its vertex is placed by solving the quadratic error function `min Σ (nᵢ·(x-pᵢ))²` for the point best satisfying all those tangent planes at once (new `qef.rs`: `AᵀA` accumulated incrementally, inverted by **pseudo-inverse** via a cyclic-Jacobi symmetric eigen-decomposition). The pseudo-inverse is the load-bearing detail — `AᵀA` is singular exactly in the common cases (a flat patch leaves two directions unconstrained, an edge one), so a plain solve would fling the vertex to infinity; dropping the near-zero eigenvalues and solving relative to the **mass point** keeps those directions at a sane in-cell position, which also makes flat regions degrade gracefully back to surface-nets behavior. Edge crossings are refined by regula falsi against the real field instead of one linear interpolation, so curved and `smooth_union`-blended surfaces get accurate hermite data too. The solved vertex is **clamped into its own cell**: dual contouring's textbook failure is an ill-conditioned solve spiking a vertex outside its cell and self-intersecting the mesh, and the clamp bounds that to "no worse than surface nets" while leaving every well-conditioned feature where it was solved. Topology is untouched — both methods share the same dual quad stage, so triangle counts match exactly and output stays watertight. **Measured on a 20 mm cube at `--res 32`: max vertex deviation 0.0000 mm and volume 8000.00 mm³ (both exact) versus 0.4167 mm and 7932.05 mm³ for surface nets** — and surface nets' error is a fixed ~⅔ of a cell at *every* resolution, so refining the grid never sharpened the feature, it only shrank the rounded region. On a cube rotated off the grid axes the part's own size tells the same story: dual contouring reproduces the analytic bounding box to 4 decimals while surface nets comes up **1.72 mm short**, having shaved the corner away — an undersized print. `bsc cad mesh` now reports a **deviation** pair (max/mean `|SDF|` over the mesh's vertices) so the sharpness is a number a caller can branch on rather than something to eyeball, and `--method dual|surface-nets` selects the polygonizer (dual is the default; the old placement is kept only so the difference stays measurable). The harvest judged each candidate ALONE, so every such import counted as a dangling one and the candidate was reported `buildable: false` — honest but **pessimistic**, and measurably so: harvesting this repo's own `src/shared/ui` produced 93 candidates of which **51 were unbuildable purely for `@/…` imports**, while **129 of the 150 `@/…` specifiers in that harvest pointed at other components in it**. Buildability is now decided against the in-set candidates, and the same imports become `composes` edges (by NAME, the component graph's key — including a sibling handed to a render prop, which no JSX tag records). **Measured on the same harvest: 42 → 76 of 93 buildable, and all 17 still held back are held back by a genuine non-component module** (`@/shared/hooks/useDragResize`, `@/shared/lib/core/format`, `@/shared/ui/layout/space`, …) — app state, a store, a shared hook and a feature's logic still make a candidate unbuildable with its reason naming the specifier, which is the honest half and is untouched. **The resolved import is KEPT in the emitted `srcText`, not elided.** Dropping it and leaning on kit resolution was the other option and would have been wrong: the preview resolves a sibling by walking the source's own import specifiers and vendoring what they land on, so the statement is load-bearing twice — it is the only record of WHICH sibling to vendor, and it binds the identifier the JSX then renders. Elide it and esbuild still bundles the module happily (a free identifier is just a global reference), so the candidate would report `buildable: true` and then throw `ReferenceError` at render — trading an honest flag for a silent runtime failure, which is the exact degradation this extractor exists to prevent. **Resolution is by name AND module, because either alone is wrong:** a name-only rule would forgive `import { Button, useAppStore } from "@/store"` merely because some `Button` was harvested; a path-only rule can't compare across roots. So an import resolves when a binding names a harvested component AND the specifier names that component's module — compared on the segment-aligned shared tail, since the harvest root is rarely the `@/` alias root (a candidate carries `controls/Button` while the specifier says `@/shared/ui/controls/Button`).
